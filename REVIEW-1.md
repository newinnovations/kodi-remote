# KodiRemote review

**Scope:** source, project configuration, and release script reviewed on 2026-08-16. The repository is a compact WPF controller with a clear purpose, sensible bounded in-window logging, and cleanup for the registered window hook. No automated tests, CI configuration, or user-facing documentation are present. A build could not be run in this environment because the .NET SDK is not installed (`dotnet: command not found`).

## Priority findings

| Priority | Finding | Evidence and impact | Recommended change |
| --- | --- | --- | --- |
| High | 1. Polls and hotkey commands can run concurrently, producing stale or conflicting UI state. | `DispatcherTimer.Tick` starts an `async` lambda without awaiting it, an initial fetch is also fire-and-forget, and each hotkey starts another command and fetch (`MainWindow.xaml.cs:98-102`, `141`, `147-176`). A slow Kodi connection can leave multiple `FetchKodiStatusAsync` calls in flight. All JSON-RPC requests also use `id = 1` (`494-502`), so responses cannot be correlated if the transport is later parallelized. | Serialize state refreshes and commands with a `SemaphoreSlim` or a single background work queue; skip or cancel a tick while one is active. Use monotonically increasing JSON-RPC IDs and only apply the newest completed snapshot. |
| High | 2. Communication failures are reported as “nothing playing,” hiding outages and authentication/configuration failures. | `SendKodiRequestAsync` catches every exception and returns `default` (`505-537`). It does not call `EnsureSuccessStatusCode`, so HTTP 401/500 bodies are treated as normal JSON. `FetchKodiStatusAsync` interprets the resulting undefined value as no active player and clears the display (`243-256`). | Return a typed success/error result (or throw a specific transport/protocol exception to a caller that handles it). Treat non-success HTTP responses and JSON-RPC `error` as failures, preserve the prior playback state, and display a distinct connection/error status with actionable detail. |
| High | 3. Kodi credentials are stored as plaintext next to the executable and sent through an insecure default URL. | `KodiSettings` serializes `Username` and `Password` to `settings.json` under `AppContext.BaseDirectory` (`KodiSettings.cs:9-11`, `34-35`); the default is `http://localhost:8080/jsonrpc` (`7`). Basic authentication only base64-encodes credentials (`MainWindow.xaml.cs:66-70`). The file may also be non-writable when the app is installed under Program Files. | Store settings in a per-user application-data directory. Protect secrets with Windows DPAPI/Credential Manager, do not persist a password where possible, and require/strongly prefer HTTPS for non-loopback hosts. Validate URL and writability before startup, with a visible configuration error rather than a crash. |
| High | 4. Unexpected Kodi response shapes can terminate fire-and-forget work and leave the UI silently stale. | Several fields use `GetProperty`, `GetInt32`, `GetDouble`, and `GetBoolean` without checking type or existence (`181-184`, `191-193`, `279`, `294`, `319-328`, `368-370`, `449-452`). Exceptions from the timer lambda and discarded fetch task have no observation path (`98`, `102`, `141`). Kodi version differences, a proxy error page, or incomplete metadata can therefore surface as unhandled async exceptions. | Deserialize into validated DTOs or introduce defensive `TryGet*` helpers for every optional API field. Handle exceptions at each fire-and-forget boundary, log the operation and error, and keep the polling loop alive. |
| Medium | 5. The UI layer owns configuration, Win32 interop, HTTP/JSON-RPC protocol, polling, parsing, and presentation. | `MainWindow` spans 575 lines and directly changes controls, makes requests, and contains protocol and formatting logic. `SubtitleTrackItem` is mutable and has no change notification (`SubtitleTrackItem.cs`). | Split into an `IKodiClient`, a polling/controller service, typed response models, and a view model with observable properties/collections. This enables unit tests without WPF or Kodi and removes repeated imperative UI updates. |
| Medium | 6. Hotkey registration failures are ignored and the success log is unconditional. | Return values from all five `RegisterHotKey` calls are unused (`89-95`), while the log always says they were registered. Hotkey collisions are common on media PCs, so the primary control path can fail without user feedback. | Check every return value, retrieve and log the Win32 error, show the unavailable bindings in the UI, and unregister only successfully registered IDs. Make bindings configurable and consider a conflict-free fallback. |
| Medium | 7. Shutdown does not cancel outstanding work or dispose network resources. | `OnClosed` stops the timer and unregisters hotkeys but does not cancel request tasks or dispose `_httpClient` (`563-572`). A pending continuation can still attempt a dispatcher update during teardown. | Maintain a window-lifetime `CancellationTokenSource`, pass its token to every HTTP call, cancel it during closing, guard UI updates after disposal, and dispose the HTTP client/CTS. Set a finite HTTP timeout. |
| Medium | 8. Settings recovery silently discards diagnosis and can still fail at startup. | `KodiSettings.Load` catches all read/deserialization failures with no logging (`15-28`) and immediately calls `defaults.Save()` outside a catch (`30-31`). A corrupt file is overwritten; an unwritable deployment directory throws from the constructor path. | Catch only expected I/O/JSON exceptions, retain/rename a corrupt file, report the exact issue, and make save failures explicit. Validate required settings and support a configuration UI or command-line/env override. |
| Medium | 9. There is no regression safety net or reproducible build/release automation. | No test project, solution, CI workflow, analyzer settings, version metadata, or dependency lock policy is tracked. `release.ps1` is a single publish command with a commented manual copy step. | Add unit tests for JSON parsing, subtitle labels, elapsed/end-time calculation, configuration validation, and failed transport behavior; add an integration contract test against a mocked Kodi endpoint. Add CI to restore, build, test, and publish. Make release publishing parameterized, versioned, signed as appropriate, and fail on errors. |
| Low | 10. Layout and accessibility are fragile on varied displays and assistive technology. | The window starts borderless and non-resizable, then hard-codes `1400x800` when toggled (`MainWindow.xaml:5`, `MainWindow.xaml.cs:110-115`). Large fixed font sizes, color-only subtitle selection, and no accessible names/key alternatives are present. | Use responsive sizing/minimums and DPI-aware layout, preserve the user’s size, expose commands with keyboard access, add automation properties, and avoid communicating state through color alone. |
| Low | 11. The request/refresh path is unnecessarily chatty. | One status refresh makes at least four sequential HTTP requests: active player, properties, item, and view mode (`243-265`); command paths repeat active-player lookups and then refresh. | Use JSON-RPC batch requests where Kodi supports them, pass a known player ID through a command flow, and cache immutable/slow-changing data. This reduces latency and makes overlap less likely. |

## Strengths to retain

- A single `HttpClient` is reused rather than created per request.
- Status/log output is bounded (`MaxLogChars`) and connection transitions are not logged repeatedly.
- Subtitle labels account for language aliases and accessibility-related track flags.
- The application removes its WndProc hook and unregisters hotkeys when the window closes.
